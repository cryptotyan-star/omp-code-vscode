## 1. Вердикт

1. **Форкнуть приложение Superset внутрь VS Code — нельзя.** `apps/desktop` — Electron 41 main-process (dock badge через `app.dock.setBadge`, `dock-icon.ts:266-273`; spawn `host-service` как child, `host-service-coordinator.ts:1-40`; `pty-daemon` на node-pty), renderer — React 19 + Tailwind 4 + radix + tRPC/Hono/WS. Extension host VS Code — Node без Electron API, webview — один `postMessage`; OMP Code webview — vanilla JS (`media/main.mjs`, ~4k LoC). Ничего из UI/main-tier Superset не переносится.
2. **Форкнуть пакеты — только точечно.** Единственный пакет, который стоит брать почти как есть: `packages/port-scanner` (~1.3k LoC, только `pidtree`, `scanner.ts:1-50`). Как справочник по поведению (не код): `host-service/src/trpc/router/git/utils/git-status.ts`, `git-helpers.ts:171-204, 521-556` (3-dot diff + merge-base), `workspaces.ts:341-440` (`git worktree add --no-track -b` + `branch.<b>.base`), `workspace-creation/shared/git-config.ts:3-20` (`push.autoSetupRemote`), `runtime/setup/config.ts:11-27` (схема `.superset/config.json`). НЕ брать: `host-service` целиком (47k LoC, `createApp` требует `cloudApiUrl` + `ApiAuthProvider`, `app.ts:41-56`; better-sqlite3; Hono), `pty-daemon` (node-pty ABI, `README.md:16-30`), `chat-runtime` (свой journal на sqlite — omp уже пишет JSONL), `ui`/`chat-ui`/`panes`/`workspace-client` (React). Полный список — §4.
3. **Движок omp уже есть.** `task` tool спавнит субагентов in-process (`omp/task/executor.ts:2646`), семафор `task.maxConcurrency=32` (`settings-schema.ts:4597`), async jobs (`async/job-manager.ts`), эфемерная изоляция через PAL-бэкенд (APFS clone / btrfs / zfs / reflink / overlayfs / ProjFS / block-clone / rcopy, `settings-schema.ts:4452-4470`) в `~/.omp/wt/t<9hex>/m` с отвязанным `.git` (`worktree.ts:422-471`, `git.detachGitDir`) и захватом результата patch/branch (`worktree.ts:763-960`; `isolation-runner.ts:281-402`), Agent Hub TUI (`modes/components/agent-hub.ts`). Через RPC это наблюдаемо (`set_subagent_subscription`/`get_subagents`/`get_subagent_messages`, `rpc-mode.ts:1143-1179`), но НЕ управляемо: нет RPC на spawn/kill/steer/revive (`rpc-types.ts:28-93`), изоляция живёт только в пределах вызова `task` и не является git worktree/веткой, которую увидел бы VS Code, host tools не наследуются субагентами (`session-tools.ts:1553-1600`, `executor.ts:3123`).
4. **UI и оркестрацию строить нативно на VS Code API.** Workspace = git worktree: жизненный цикл через CLI `git worktree add --no-track -b` (тестируемо в `node --test`), интеграция с UI через built-in git API (`api.openRepository`, `toGitUri`, `Repository.state`, `merge/createStash/migrateChanges`); один `omp --mode rpc-ui --cwd <worktree>` на workspace — это ровно текущая модель OMP Code (`ompProcess.ts:97`, `extension.ts:104-148` уже принимает `forcedCwd`); board — рефакторинг `sessionBoard.ts` на `window.createTreeView`; diff — `vscode.diff`/`vscode.changes` + `api.toGitUri`; терминалы — `window.createTerminal({cwd})`; API оркестрации — `set_host_tools` (omp) + `lm.registerMcpServerDefinitionProvider` (VS Code ≥1.101).
5. **Недостижимо внутри VS Code:** dock badge (нет API); чтение вывода произвольных терминалов (`onDidWriteTerminalData` — proposed, «не будет стабилизирован», `proposed.terminalDataWriteEvent.d.ts:8-12`); авто-порты (`PortAttributesProvider`, `openTunnel` — proposed); cron-автоматизации без открытого окна; регистрация omp как harness в Agents window (`chatSessionsProvider` — proposed); cloud relay/hosts как у Superset; PR-flow Superset (checks, review threads, `gh pr merge`) — делегировать встроенному GitHub PR extension, не переписывать.
6. **Лицензия:** ELv2 non-sublicensable (`LICENSE.md:9`) — форкнутый код не становится MIT. Если что-то копируется: код в `src/vendor/superset/`, но `LICENSE-ELv2.md` + `NOTICE`/`THIRD-PARTY-NOTICES.md` — в **корне репозитория** (`.vscodeignore` исключает `src/**` и `**/*.ts`, так что ничего под `src/` в `.vsix` не попадает), заголовки файлов — `/*! Derived from … */` + `legalComments: "inline"` в `esbuild.mjs` (обычные комментарии esbuild вырезает). Рекомендация — clean-room для всего кроме `port-scanner` (и даже его проще переписать: ~300 LoC), тогда обязательств нет.

Итог: не «форк Superset», а «Superset-подобный слой оркестрации в OMP Code» — ~6k LoC поверх существующих 11.7k, spike + пять фаз; ценность даёт связка Phase 1 + Phase 2 (worktree + review), Phase 0 (наблюдение субагентов) — параллельная и необязательная.

### 3.1 Один процесс на workspace vs внутренние субагенты omp — оба, с чёткой границей

**Внутренние субагенты (`task` tool) — model-driven fan-out внутри одного чата.** Использовать когда: модель сама решает разбить задачу (scout/reviewer/librarian), результат нужен ей же в контекст, работа короткая, изоляция либо не нужна, либо достаточно эфемерной PAL-изоляции (`isolated:true` — **только** при `task.isolation.mode≠none`: при дефолтном `none` это preflight-ошибка спавна, `structured-subagent.ts:296-302`). Плюсы: нулевая стоимость для расширения (один процесс, один набор ключей), готовый semaphore/бюджет/yield-протокол, `AgentProgress` с cost/tokens/currentTool (`task/types.ts:398-471`), автодоставка результата. Минусы: нет RPC на kill/steer/revive (`rpc-types.ts:28-93`); со стороны модели `hub` (`tools/hub/index.ts:74-82`) даёт `send {to:<agentId>}` (будит idle, оживляет parked через lifecycle manager, `hub/messaging.ts:1-10`) и `cancel {ids}` **по id async-job**, а не по agent id — прямого kill агента у модели нет; `/collab` (`slash-commands/builtin-collaboration.ts:255`, `collab/host.ts:602-629`) — relay-канал для гостей, не для расширения. Нет долгоживущего worktree (изоляция — CoW-клон с отвязанным `.git`, не ветка). **Approvals субагентов не приходят вовсе**: `executor.ts:896-899` принудительно ставит `"tools.approvalMode": "yolo"` — любой `task` внутри чата с `always-ask` выполняет edit/bash без вопросов, ограничитель только `tools.approval` policies omp. Host tools недоступны субагентам (`executor.ts:3123`). Расширение здесь — **наблюдатель** (Phase 0) + предупреждение в UI.

**Workspace-процессы (`omp --mode rpc-ui --cwd <worktree>`) — human-driven параллельные задачи.** Использовать когда: человек ставит 2-5 независимых задач, каждая должна жить в своей ветке часами, нужны собственный терминал/порты/diff, approvals должны идти человеку, нужен per-agent steer/abort/restart/switch_session, разные модели и approval-tier, выживание после перезапуска VS Code (`switch_session` на JSONL в `~/.omp/agent/sessions/<enc(cwd)>/`). Всё это RPC даёт только для top-level сессии — значит, top-level сессия и должна быть единицей workspace. Цена: ~400 МБ RSS на процесс (§6.1) и N worktree с зависимостями (§6.2) — отсюда лимит процессов и «парковка» idle-workspace (Phase 1).

**Мост между ними:** main-сессия получает host tools `workspace_*` (§3.2), так что модель тоже может поднять долгоживущий workspace, когда `task` не подходит — например, «сделай три альтернативные реализации, я выберу». Правило для промпта/системной заметки: «`task` — для разведки и ревью (без `isolated`, если `task.isolation.mode=none`); `workspace_create` — для реализаций, которые надо сравнивать или мержить».

### 3.2 Host-tool bridge (`set_host_tools`)

После handshake (`ompSession.ts:910-980`) main-сессия отправляет `{type:"set_host_tools", tools:[...]}` (`rpc-types.ts:45, 434-442`; обработчик `rpc-mode.ts:1127-1132`). Набор (JSON Schema `parameters` — объект, `rpc-mode.ts:503-506`):

| name | parameters | результат (`content:[{type:"text"}]` + `details`) |
|---|---|---|
| `workspace_create` | `{name, branch?, base?, prompt?, model?, approvalMode?, runSetup?, maxCostUsd?}` | `{id, path, branch, sessionId}`; при превышении `ompcode.maxWorkspaceProcesses` — `isError` с текстом «park or delete a workspace first» |
| `workspace_list` | `{}` | строки board: id, branch, status (`parked|starting|working|asks|idle`), cost, +/-, ports; итоговая сумма cost |
| `workspace_prompt` | `{id, message, mode:"prompt"\|"steer"\|"follow_up"}` | ack; parked workspace спавнится лениво |
| `workspace_wait` | `{ids[], timeoutMs, until:"idle"\|"asks"}` | статусы + cost + `get_last_assistant_text` каждого; шлёт `host_tool_update` каждые ~5 с; отменяется `host_tool_cancel` |
| `workspace_diff` | `{id, path?, maxBytes?}` | numstat vs merge-base или patch файла (обрезка по `maxBytes`) |
| `workspace_merge` | `{id, strategy:"merge"\|"rebase"\|"apply", deleteLosers?}` | результат/конфликты |

Протокол на стороне расширения (`src/hostTools.ts`): `host_tool_call {id, toolCallId, toolName, arguments}` → `HostToolBridge.execute(name, args, {signal, sendUpdate})` → 0..n `host_tool_update {id, partialResult}` → `host_tool_result {id, result, isError?}`; `host_tool_cancel {targetId}` → `AbortController.abort()` (`host-tools.ts:122-184`; `rpc-types.ts:445-473`). Кадры `host_tool_result/update` — control frames, идут мимо очереди (`rpc-mode.ts:279-302`), поэтому `workspace_wait` не блокирует `abort`. На stdin EOF omp сам отклоняет pending (`host-tools.ts:195-203`). Ограничения: имена не должны совпадать с builtin (`session-tools.ts:1553-1600`, ошибка «conflicts with an existing tool»); host tools видны только top-level сессии — оркестратором может быть только main chat, не субагент; `set_host_tools` вызывать до первого промпта (mid-turn поведение не трассировано — spike, §5).

Дополнительно `set_host_uri_schemes` (`rpc-types.ts:46, 479-501`): схема `workspace://<id>/diff`, `workspace://<id>/transcript`, `workspace://<id>/ports` — модель читает их обычным `read`, экономя вызовы tools. Объявлять `{scheme:"workspace", writable:false, immutable:true}`; обрабатывать три кадра: `host_uri_request {id, operation:"read"|"write", url, content?}` → `host_uri_result {id, content, contentType:"text/markdown"}` (на `operation:"write"` — `isError`, схема не writable), и `host_uri_cancel {id, targetId}` (`rpc-types.ts:497-501`; `host-uris.ts:154` шлёт его при abort) → прервать чтение diff/transcript. `immutable:true` отключает hashline-якоря.

## 6. Риски и неизвестные

1. **Одна сессия на процесс rpc-ui** (`rpc-mode.ts:662-668, 469-494`): N workspace = N Bun-процессов с полным набором tools/MCP/LSP каждый. **Измерено** (`scratchpad/ompmeasure/out.txt`): idle `omp --mode rpc-ui` 17.3.5 = 319 600 KB RSS bun + ~50 МБ node-child + ~24 МБ python ≈ 400 МБ; `ready` 0.40 с; 5 workspace + main ≈ 2–2.4 ГБ до первого токена. Ответ — `maxWorkspaceProcesses` (3), парковка idle, lazy spawn (Phase 1). ACP-режим даёт много сессий на процесс, но без subagent frames и host tools (`acp-agent.ts:476-538`) — не альтернатива. omp умирает без ключей провайдера (memory: «omp без ключей умирает») — расширение уже инжектит env (`ompSession.ts:218`), каждый процесс наследует.
2. **Worktree + зависимости**: `git worktree add` не копирует `node_modules`; `git.worktreeIncludeFiles` — только gitignored по glob (`.env`), не для `node_modules`. Варианты: setup-скрипт `pnpm install --offline` / `npm ci`, symlink на `node_modules` main-checkout (ломает native builds и watchers), pnpm store. По умолчанию — setup-скрипт + предупреждение о диске. Superset решает так же (никакого копирования, только `setup[]`).
3. **Надёжность статуса**: для omp rpc-ui статус детерминирован (`agent_start/agent_end`, `uiPendingIds`, `ompSession.ts:280-291`) — лучше, чем hook-подход Superset (`Stop` не срабатывает на Ctrl+C, `useTerminalInterruptClear.ts:21-74`). Слабые места: `agent_end` при крэше процесса — уже обрабатывается (`proc.onExit` чистит board); субагенты внутри процесса — только по lifecycle-кадрам, при `subscription=off` невидимы; **субагенты работают в yolo независимо от `--approval-mode` (`executor.ts:896-899`)** — это UX/safety-сюрприз для пользователя с `always-ask` (флаг всегда передаётся, `ompProcess.ts:97-103`), а не проблема атрибуции — бейдж в Phase 0; «review» (закончил, но человек не смотрел) — `lastSeenAt` per workspace как в `deriveTerminalAgentStatus.ts:17-23`.
4. **ELv2**: если что-то копируется — код в `src/vendor/superset/`, лицензия/NOTICE в корне (`.vscodeignore` режет `src/**`), `/*!`-header + `legalComments:"inline"`, проверка `vsce ls`; расширение становится «MIT AND Elastic-2.0» навсегда; `remote-relay/` держать чистым от Superset-кода (§13 hosted service). Рекомендация — clean-room; тогда обязательств нет.
5. **Дрейф версии omp**: OMP Code не пинит omp (`ompcode.ompPath` default `"omp"`, установлен 17.3.5). Минимумы по `omp/CHANGELOG.md`: `set_host_tools` + `host_tool_*` — **14.0.0** (2026-04-08, `:7172-7212`); `set_host_uri_schemes` — **15.0.2** (`:5718-5722`); `set_subagent_subscription`/`get_subagents`/`get_subagent_messages` — **15.10.12** (`:4067-4071`). Полный набор — ≥15.10.12; probe через `diagnostics.ts` `runVersion` (`:28`) + деградация по фичам (error-response на `set_subagent_subscription`/`set_host_tools` → скрыть панель/оркестрацию); минимальная версия в README/INSTALL. Формы кадров (`AgentProgress`, `RpcHostToolDefinition`) не версионируются — `negotiate_protocol` знает только v2 (`rpc-mode.ts:980-984`) — держать парсинг lenient.
6. **Windows** (`src/winLaunch.ts`): omp через `omp.cmd` → cmd.exe с ручным квотингом — пути worktree с пробелами уже учтены; `git worktree` пути длиной >260 — включать `core.longpaths`; `git worktree remove` при живом процессе в каталоге — EBUSY → порядок удаления из Phase 1; порт-скан через `netstat -ano`; shell integration в PowerShell медленнее; `lsof` отсутствует. Тестировать Phase 1/3 на Windows отдельно.
7. **Версии VS Code**: `engines.vscode`/`@types/vscode` сейчас `^1.85.0` (`package.json:18, 367`). По `git.d.ts` тегов: `createWorktree/deleteWorktree/migrateChanges` — 1.107; `diffBetweenWithStats`, `state.worktrees` — 1.108; `rebase`, `generateRandomBranchName` — 1.111; `createWorktree({noTrack})` — **1.116** (в 1.113.0 и 1.115.0 ещё нет). MCP provider — 1.101, `TerminalShellExecution` — 1.93, `ViewBadge` — 1.72. Решение: `engines ^1.111.0`, `@types/vscode ~1.111.0`, `git.d.ts` вендорить с тега 1.111.0 (тогда `noTrack` не компилируется — CLI-путь для worktree обязателен по конструкции); `createWorktree` git API не использовать.
8. **`updateWorkspaceFolders`** может перезапустить extension host при переходе single→multi-root (`index.d.ts:13911-13918`) — убьёт все omp-процессы. По умолчанию worktree — только cwd агента, не workspace folder; «Add to workspace» — явное действие с предупреждением.

## 7. Что НЕ делать

- Не форкать `apps/desktop`, `host-service`, `pty-daemon`, `chat-runtime`, tRPC/Hono/WS-слой, React UI — ни один из них не запускается в extension host / vanilla webview без переписывания.
- Не запускать агентов как PTY с текстовыми промптами и не ставить lifecycle-хуки в `~/.claude`/`~/.omp/agent/extensions` (`agent-setup`) — rpc-ui даёт структурный статус, approvals, cost и transcript; PTY-путь нужен только для чужих агентов (claude/codex), что вне scope.
- Не реализовывать dock badge, `PortAttributesProvider`, чтение вывода произвольных терминалов, регистрацию omp в Agents window — proposed/отсутствующие API, Marketplace не пропустит.
- Не тянуть cloud-фичи: relay, automations на Postgres, tasks/Linear, pages, billing, `@superset_sh/sdk` (HTTP-клиент облака).
- Не переписывать PR-flow Superset (`github`, `pull-requests`, `gh pr merge`, checks, review threads) — это GitHub Pull Requests extension; наш «merge winner» — локальная операция над worktree, а не PR.
- Не делать собственный split-pane движок (`panes`) — editor groups + `TerminalLocation` + `ViewColumn`.
- Не дублировать journal в sqlite — JSONL omp + `src/sessions.ts`.
- Не включать `task.isolation.mode` как механизм workspace — это PAL CoW/overlay/copy-клон с отвязанным `.git` (`worktree.ts:422-471`), эфемерный и не наблюдаемый через RPC, не git-ветка для VS Code; оставить его для model-driven `task` с `isolated:true` — и помнить, что при дефолтном `none` это ошибка спавна.
- Не использовать RPC `bash` для пользовательских терминалов — не из-за очереди (bash идёт в фоне, `rpc-mode.ts:328-342`), а потому что это не PTY: нет стриминга/shell integration, результат одним кадром, живёт только с процессом omp; VS Code терминал.
- Не полагаться на `Repository.createWorktree({noTrack})` — до 1.116 опция молча игнорируется; CLI `git worktree add --no-track -b`.
- Не рестартовать все сессии на любое изменение `ompcode.*` — per-session scoping.
- Не делать AI-именование веток через mastra — `generateRandomBranchName()` git API (1.111+) или one-shot `omp --mode json`.
- Не пытаться сделать «Superset в одном webview» — вся ценность VS Code в нативных SCM/diff/terminal/tree; webview — только чат.
