# Промт для GLM 5.2 — очередь сообщений + восстановление транскрипта

Скопировать блок ниже целиком в первое сообщение сессии GLM. Запускать GLM из корня
проекта (`~/Desktop/Ohmypi`), чтобы он мог читать упомянутые файлы.

```text
Ты работаешь над VS Code-расширением OMP Code (~/Desktop/Ohmypi). Это чат-панель поверх
CLI-агента `omp`, общение по RPC (`omp --mode rpc-ui`). Расширение — только GUI.

Твоя задача — реализовать ДВЕ фичи и вывести результат текстом: полные изменённые файлы
или точечные патчи по файлам + новые тесты + дополнения локализации. Ничего не запускай
и не пиши в файлы — только выведи код.

===============================================================================
КАРТА ПРОЕКТА
===============================================================================

- `src/ompSession.ts` (~2135 строк) — хост: один OmpSession = один OmpProcess + один
  прикреплённый вебвью. Метод `onWebviewMessage` (~строка 683) — свитч по `msg.t` от
  вебвью. Метод `post(obj)` шлёт JSON в вебвью. Метод `request(obj)` — RPC-запрос к omp.
- `media/main.mjs` (~2699 строк) — вебвью, один IIFE, стиль ES5: `var`, function
  declarations, никаких классов и стрелок в горячих путях. `post(obj)` шлёт хосту,
  входящие сообщения разбираются в большом свитче (~строка 2474+, `case "boot"`,
  `case "reset"`, `case "transcript"` ...), кадры агента — в `handleFrame(f)`
  (~строка 2405, `case "agent_start"`, `case "agent_end"` ...).
- `media/main.css` — стили вебвью.
- `l10n/ru.json` — русские переводы. Ключ = английский исходный текст.
- `test/` — node --test --experimental-strip-types. Релевантные: `webviewWiring.test.ts`,
  `l10n.test.ts`, `sessions.test.ts`.

Команды проверки (выполнит человек, но код обязан им соответствовать):
  npm run test        # typecheck + все тесты
  npm run typecheck   # tsc --noEmit

===============================================================================
ЖЁСТКИЕ ПРАВИЛА (нарушение = падение тестов или немой баг)
===============================================================================

1. ЛОКАЛИЗАЦИЯ. Каждая новая пользовательская строка — через `t("English source")`.
   Ключ — английский текст. КАЖДЫЙ новый ключ ОБЯЗАН быть добавлен в `l10n/ru.json`
   с русским переводом; `{0}`-плейсхолдеры в ключе и переводе обязаны совпадать.
   `test/l10n.test.ts` сканирует исходники и ПАДАЕТ на непереведённой строке.
2. Никогда не объявляй локальную переменную/параметр с именем `t` в файлах,
   импортирующих перевод, и не читай свойства у функции `t` — на это есть тест.
3. В `src/*.ts` кросс-импорты значений — с расширением `.ts`
   (напр. `import { x } from "./l10n.ts"`), иначе ESM-резолвер тестов не загрузит модуль.
4. Не меняй RPC-протокол с omp и формат сообщений хост↔вебвью, кроме явно оговорённого
   ниже. Никаких новых зависимостей. Минимальный дифф, стиль соседнего кода.
5. В `media/main.mjs` — только `var` и function declarations, как вокруг.

===============================================================================
ФИЧА A. ОЧЕРЕДЬ СООБЩЕНИЙ ВО ВРЕМЯ РАБОТЫ АГЕНТА (только media/main.mjs + main.css + l10n)
===============================================================================

СЕЙЧАС. `sendPrompt()` (~строка 2152) отправляет всегда сразу: `post({t:"prompt", ...})`,
локальный bubble, `setWorking(true)`. Если агент стримит, хост передаёт
`streamingBehavior:"steer"` — сообщение вмешивается в текущий ход. Пользователь не может
выстроить несколько инструкций, пока агент занят.

СОСТОЯНИЕ, которое уже есть в main.mjs:
- `var working = false;` (~108), функция `setWorking(on)` (~629).
- `handleFrame`: `case "agent_start": setWorking(true)` и `case "agent_end":
  setWorking(false); currentAssistant = null;` (~2411-2419).
- `case "promptFailed": setWorking(false); if (pendingLocalUser>0) pendingLocalUser--;`
  (~2505).
- `resetView()` (~2384) — полная очистка вью при `{t:"reset"}`.
- Кнопка Stop: `btnStop.addEventListener("click", function(){ post({t:"abort"}); })`
  и глобальный Escape (~2279): `if (working) post({t:"abort"});`.

ТРЕБУЕМОЕ ПОВЕДЕНИЕ:
1. Если `working === false` — `sendPrompt()` работает ровно как сейчас.
2. Если `working === true` — Enter/клик по Send НЕ отправляет, а ставит сообщение
   (текст + текущие готовые attachments) в очередь:
   - вводится `var promptQueue = [];` — элементы `{ text: string, files: array }`.
   - над композером рендерится ряд чипов (по одному на элемент очереди): усечённый
     текст (первая строка, ~60 символов) + крестик удаления. Клик по крестику удаляет
     элемент из очереди. Сам чип не кликабелен иначе.
   - поле ввода и attachments очищаются сразу (как при отправке), toast не нужен.
   - в `promptHistory` текст попадает ТОЛЬКО при реальной отправке (см. п.3), не при
     постановке в очередь.
3. Сброс очереди: извлеки из `sendPrompt()` тело реальной отправки в отдельную функцию
   (например `dispatchPrompt(text, files)`): `post({t:"prompt",...})`, promptHistory,
   `pendingLocalUser++`, `addUserBubble`, `setWorking(true)`, `stuck = true`,
   `scrollBottom()`. Её же вызывает и сброс очереди.
4. Автосброс очереди (flush): когда ход завершается и очередь непуста — отправить
   ПЕРВЫЙ элемент через `dispatchPrompt`. Точки срабатывания: `case "agent_end"` и
   `case "promptFailed"`. FIFO, по одному сообщению на ход; следующий элемент уйдёт
   после `agent_end` предыдущего.
5. КРИТИЧЕСКИЙ edge case — прерывание. Пользователь нажал Esc/Stop → придёт
   `agent_end`, и flush НЕ должен сработать (после «останови» агент не должен тут же
   получить следующее сообщение). Реализация: `var abortRequested = false;` —
   выставляется в `true` в обработчике btnStop и в ветке Escape (`if (working)`),
   проверяется и сбрасывается в `agent_end`: если был `abortRequested` — очередь
   остаётся нетронутой, flush не выполняется. На случай гонки сбрасывай флаг также в
   `agent_start` (новый ход = прежнее прерывание отработано).
6. `resetView()` обязан очищать `promptQueue` и удалять ряд чипов (новая сессия /
   смена сессии — чужая очередь недопустима).
7. Строки через `t(...)`: как минимум тултип крестика `t("Remove from queue")`.
   Подписи-подсказки в композере не требуются.
8. CSS в `media/main.css`: `.queue-row` (flex, wrap, gap, отступ над композером) и
   `.queue-chip` (в стиле существующих чипов композера — посмотри соседние классы,
   переиспользуй переменные темы, НЕ вводи новых цветов; учти `ompcode.accentColor` —
   чипы должны наследовать акцент через существующие CSS-переменные).
   HTML-скелет генерируется хостом в `src/ompSession.ts` (метод getHtml, ~строка 2100):
   добавь пустой контейнер `<div id="queue-row" class="queue-row hidden"></div>`
   непосредственно перед `<footer class="composer">`. Это ЕДИНСТВЕННОЕ изменение в
   `ompSession.ts` для фичи A — покажи точный фрагмент до/после.
9. Скрытие/показ ряда: класс `hidden`, когда `promptQueue` пуст.

ТЕСТЫ для фичи A: посмотри `test/webviewWiring.test.ts` — если там есть харнесс,
загружающий main.mjs с DOM-заглушкой, добавь кейсы: (а) отправка при working=true не
шлёт `prompt`, а кладёт в очередь и рисует чип; (б) `agent_end` после обычного хода
отправляет ровно один queued prompt; (в) `agent_end` после abort НЕ отправляет;
(г) `{t:"reset"}` очищает очередь. Если харнесса для такого уровня нет — покрой, чем
позволяет существующая инфраструктура, не строй новую.

===============================================================================
ФИЧА B. ВОССТАНОВЛЕНИЕ ТРАНСКРИПТА ПОСЛЕ ПЕРЕЗАГРУЗКИ ВЕБВЬЮ (src/ompSession.ts + тест)
===============================================================================

ПРОБЛЕМА. Смена языка/темы вызывает `reloadHtml()` (~строка 206): он ставит
`this.webviewReady = false` и пересобирает HTML. Новый вебвью шлёт `{t:"ready"}`,
но DOM-транскрипт пуст — пользователь видит пустой чат, хотя сессия omp жива.

УЖЕ ЕСТЬ всё необходимое:
- В `case "ready"` (~строка 684) в конце есть ветка ре-гидрации пересозданного вебвью:

    if (this.initialized) {
      // Webview was re-created against a live agent — re-hydrate it.
      await this.pushModels();
      await this.pushCommands();
      await this.pushState();
    }

- Точный паттерн replay есть в `resumeAfterRestart` (~строка 254) и `openSession`
  (~строка 1561):

    const data = await this.request({ type: "get_messages" });
    this.post({ t: "reset" });
    this.post({ t: "transcript", messages: this.extractList(data, "messages") });

- Вебвью умеет принимать: `case "reset"` → `resetView()`, `case "transcript"` →
  `renderTranscript(...)` (~строки 2680, 2544, 1060). Менять вебвью для фичи B НЕ нужно.

ТРЕБУЕМОЕ ИЗМЕНЕНИЕ — только `case "ready"`, ветка `if (this.initialized)`:
1. Переиспользуй паттерн выше: запроси `get_messages`; если список непуст —
   `post({t:"reset"})` затем `post({t:"transcript", messages})`. Итоговый порядок
   внутри ветки: pushModels, pushCommands, replay transcript, pushState (pushState
   идёт последним — `applyState` в вебвью выставляет `setWorking(state.isStreaming)`
   и не должен затираться).
2. ГУАРД: replay выполняй только когда `this.streaming === false` (поле есть, ~строка
   123). Если ход идёт прямо сейчас, live-кадры продолжат приходить сами, а replay
   дал бы дублированное недостроенное сообщение. Потеря истории при reload посреди
   хода — принимаемое ограничение, оставь в коде комментарий об этом.
3. Ошибки `get_messages` не должны ломать `ready`: оберни replay в try/catch с
   `this.output.appendLine(...)` по образцу catch в `resumeAfterRestart` (~строка 273).
4. Побочный эффект правильный и нужный: эта же ветка покрывает открытие второй
   вкладки чата к уже работающему агенту — там replay тоже корректен. Ничего
   дополнительно для этого не пиши, просто не ломай.

ТЕСТ для фичи B: посмотри `test/sessions.test.ts` / `webviewWiring.test.ts` — нужен
кейс «ready при initialized && !streaming && в сессии есть сообщения → хост шлёт reset,
затем transcript с этими сообщениями» и контркейс «streaming=true → transcript не
шлётся». Следуй существующим мокам (proc/request/post уже замоканы в этих файлах).
```

## Заметки для владельца (не часть промта)

- Запускать `glm -p "…"` из отдельной директории, НЕ из корня проекта (коллизия файла
  сессии с qwen), вывод сохранять самому. См. HANDOFF.md → «Как владелец любит работать».
- Фича A убирает steering как поведение по умолчанию (Enter во время работы = очередь,
  не вмешательство в ход) — осознанный трейдофф, как в Claude Code.
- Фича B: известное ограничение — reload посреди хода историю не восстанавливает
  (guard `!this.streaming`), комментарий об этом должен остаться в коде.
- После получения кода от GLM: `npm run test` + adversarial-ревью вторым CLI
  (`qwen -p "…"` из СВОЕЙ директории) — по сложившейся практике ловит реальные регрессии.
