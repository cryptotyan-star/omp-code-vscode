## 2. Отклонения от промпта — важно для автора

### 2.1 Инструментов `workspace_*` в среде не оказалось

Промпт написан под `workspace_create / wait / prompt / diff / verify / merge / delete`. В сессии исполнения их нет (проверено по списку смонтированных инструментов). Оркестрация выполнена эквивалентно через batch из трёх субагентов: те же границы файлов, контракты дословно, ревью диффов, возврат на доработку через прямое сообщение воркеру. Шаги merge/delete выродились: правки дизъюнктны и делались в одном дереве, вливать и удалять было нечего. **Если промпт будет переиспользоваться — стоит либо оговорить fallback, либо проверять наличие инструментов в первой строке.**

### 2.2 Модели §5 назначить было нельзя

Механизм субагентов исполнителя не даёт выбирать провайдера/модель per-worker. Принцип «не ставить дорогую модель на механику» соблюдён доступным способом: C выполнял низкоресурсный агент, A и B — стандартные. Разнесение по корзинам лимитов трёх провайдеров не потребовалось — лимиты не встретились. Долларовых счётчиков per-worker среда не отдаёт, поэтому в отчёте длительности, а не деньги.

### 2.3 Дыры в контрактах §4, закрытые решениями оркестратора

Эти решения пришлось принять и вписать в задания как обязательные — в следующей версии промпта их лучше зафиксировать явно:

1. **`ports.ts` vs `node --test`.** Тестовый раннер (`node --test --experimental-strip-types`) не резолвит модуль `vscode`. Контракт же требует `implements vscode.Disposable` и `vscode.Event`. Решение: только `import type * as vscode` (стирается) + свой минимальный `Emitter<T>`, структурно совместимый с `vscode.Event`. Без этого тест парсеров невозможен в принципе.
2. **Тест воркера A.** `terminals.ts` runtime-зависим от `vscode`, значит `test/workspaceTerminals.test.ts` не может его импортировать. Решение — инвариант-тест по исходнику, по прецеденту `workspaceManager.test.ts:346`. Промпт требовал тест, но не говорил, каким он может быть.
3. **Семантика `runConfigured` для вечных команд.** `run[]` — «long-running dev server slot» (комментарий в `types.ts`), а контрактный `Promise<{ran, supervised, exitCode?}>` обязан резолвиться. Решение: команды до последней — prep-шаги, ждём и останавливаемся на ненулевом exit; последняя стартует и **не** ждётся.
4. **Кто читает `ompcode.portScanIgnore`.** `PortScannerDeps` в §4 не имел канала для настройки, а §4C её вводит. Решение: опциональный `ignorePorts?(): number[]` в deps (потребитель — только `extension.ts`), дефолт `[22, 80, 443]`.
5. **Как «терминал открылся/закрылся» будит сканер.** У сканера нет `poke()`; из бэкофа 30 с новый dev-сервер показался бы через полминуты, нарушая критерий «не позже 3 секунд». Решение: `start()` сбрасывает на быстрый темп и сканирует немедленно — `extension.ts` дергает его по `terminals.onDidChange`.
6. **Циклическая зависимость в l10n.** `l10n.test.ts` падает и на лишнем ключе — а C должен добавить переводы строк, которые появятся в `src/` только после §6. Решение: оркестратор зафиксировал финальные английские строки заранее и передал C дословно; окно, в котором ключи «лишние», закрывается до первого полного прогона тестов. В промпте это ограничение хода стоит проговорить.
7. **`portScan*` добавлены в `HOST_ONLY_SETTINGS`** — иначе тумблер настройки перезапускал бы всех живых агентов. Промпт об этом механизме `extension.ts` не знал.

### 2.4 Внеплановый фикс: предсуществующий флак

На первом полном прогоне упал `test/workspacesGit.test.ts:171` («withRepoLock gives up rather than deadlocking») — файл фазой 3 не затронут. Диагноз: тест не дожидался фактического захвата замка; оба вызова конкурентно проходят `await canonicalPath(...)`, и под нагрузкой контендер выигрывает гонку и берёт замок первым → ожидаемого reject нет. Подтверждено перезапусками (2/3 зелёных в изоляции). Починен по праву шага 8 («красно — чини сам, это общий код»): захват сигналится из тела замка, тест стал детерминированным. Продакшен-код не трогался.
